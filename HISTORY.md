# Lesstruct Development History

> **Repo-only.** This file is not published to the docs site — it is the
> development narrative for maintainers and AI agents working in the tree.
>
> The v1 git history was squashed into the single `v1.0.0` release commit,
> so this log is the surviving record of how each phase landed, what each
> slice changed, and which decisions were superseded. Entries are
> chronological by phase; superseded claims are annotated inline.

## Phase log

- **v1 module system (Phase 1 — kernel landed)**: `kernel/` is its own Go module (`github.com/aristorinjuang/lesstruct/kernel`, pinned to the same dep versions as the main module, wired via `require` + `replace` in `go.mod`) holding the `Module`/`Kernel` contracts + capability interfaces (`module.go`), the `Principal` identity shape (`principal.go`), the typed event bus (`bus.go`), the module registry with topological `InitAll` (`registry.go`), and the database `Driver`/`Dialect` contracts (`kernel/database/`). `internal/modules/` holds transitional wrappers (names/versions/dependency edges, no-op lifecycle) registered from `main.go` — the default composition root — until Phase 3 replaces them with real modules under `modules/`. [Superseded: the event bus was removed in 5.1 (zero consumers); the wrappers were retired in 4.0e and the package now holds core-side seam adapters plus the disabled-list helpers.] `internal/database` opens connections through `Driver` implementations behind the unchanged `Open()` signature (unknown drivers now fail with both `ErrUnsupportedDriver` and a kernel `UnknownDriverError` listing installed drivers). Rule: kernel never imports modules or internals; capability discovery goes through `kernel.Capabilities[T]`, never a service locator. Terminology: Go compile-time units are "modules"; "plugins" means the WASM system only.
- **v1 identity seam (Phase 2 — Principal live)**: both auth realms attach `kernel.Principal` via the shared `newUserContext` (string keys dual-written until Phase 3); `middleware.Principal` is the request-identity accessor. Acting-user service parameters are `kernel.Principal` (content, comments, media, apikey, profile, profile-picture); target IDs, scope filters (`userID <= 0` = global), and repository signatures stay `int`. `internal/identity` bridges the two (`New`/`IntID`/`PrimaryRole`, `ErrInvalidUserID` maps to each realm's existing bad-ID response). Capability vocabulary (`admin`, `media`, `comments`, `content.publish`, `content.manage:<type>`) resolves over the role registry via `middleware.NewCapabilityResolver` (fail-closed; `kernel/conformance` ships the `CheckAuthorizer` suite); the agent import guard answers from it with byte-identical responses. `RequireCapability` middleware exists for Phase 3 route adoption.
- **v1 module system (Phase 3.0 — module-serving seam)**: `kernel/httpx` is the one response envelope modules write (byte-identical to `internal/api/response` by contract — `internal/api/response/compat_test.go` diffs both writers). `RouteProvider.RegisterRoutes` receives the core-built router (protected chain pre-applied); `PublicRouteProvider` is the anonymous counterpart — no router accessors on `Kernel` by design (smaller kernel, same power). `kernel/posttype` is the content-type discovery index populated from `Capabilities[ContentTypeProvider]` after `InitAll`; rich definitions stay in module domains. `PostTypeDef.Protected` marks slugs reserved by built-in modules.
- **v1 module system (Phase 3.0b — customfield to kernel)**: `internal/domain/customfield` moved verbatim to `kernel/customfield` (same package name; stdlib-only, shared by every content-touching module) as Published Language. All 26 import sites updated mechanically; zero behavior change.
